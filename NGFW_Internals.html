Глава 01

Linux kernel —
фундамент всего

FTD — это не монолитная прошивка. Это коллекция userspace процессов поверх обычного Linux. Понимание этого меняет всё: объясняет почему диагностика через bash реальна, почему компоненты могут рассинхронизироваться, и как пакет вообще попадает из NIC в Lina.

Архитектурный обзор: что живёт на устройстве

Когда в 2013 году Cisco приобрела Sourcefire за $2.7 млрд, она получила два несовместимых стека: ASA (Adaptive Security Appliance, корни из PIX-эпохи 90-х) с собственным почти-RTOS на голом железе — и Sourcefire FireSIGHT с его полноценным Linux окружением, Ruby on Rails management-плоскостью и Snort в качестве IPS-движка.

Вместо переписывания ASA с нуля (что заняло бы 5+ лет) инженеры пошли прагматичным путём: ASA-код был скомпилирован как обычный userspace процесс под Linux. Этот процесс назвали Lina. Результирующая архитектура — несколько тяжеловесных userspace процессов, живущих бок о бок на одном Linux kernel.

1.1 DPDK и пакетный путь

На бюджетных платформах (FTDv, Firepower 1000) пакеты идут через стандартный Linux network stack: NIC → kernel → socket → userspace. На высокопроизводительных (Firepower 4100, 9300) используется DPDK — Data Plane Development Kit.

Что такое DPDK и зачем он нужен

DPDK — библиотека Intel для работы с NIC напрямую из userspace, минуя ядро Linux. Вместо того чтобы пакет прошёл через netif → tcp_ip_stack → socket → read() — он идёт через poll-mode driver прямо в memory-mapped буфер, доступный userspace процессу.

Это устраняет несколько источников задержки:

  • System call overhead — нет перехода kernel↔userspace на каждый пакет
  • IRQ overhead — DPDK использует polling вместо прерываний
  • Memory copy — zero-copy через huge pages и DMA
  • Scheduler jitter — dedicated CPU cores пинены на DPDK потоки

Важно понимать
Lina не использует стандартный Linux TCP/IP стек для обработки трафика через firewall. У неё своя таблица состояний, свои routing table, свои ACL. Linux routing (команда route в bash) и routing внутри Lina — это разные вещи.

1.3 IPC: как компоненты общаются друг с другом

Межпроцессная коммуникация — это клей архитектуры. Понимание того, кто с кем и как разговаривает, объясняет большинство проблем с деплоем и рассинхронизацией.

Пара Механизм Что передаётся
FMC → FTFD SFTUNNEL (TLS поверх TCP) Объекты политик, команды деплоя
FTFD → Lina Unix socket (PTY) ASA CLI команды текстом
FTFD → Snort Файловая система + SIGHUP Файлы .rules, конфиг препроцессоров
Lina → Snort DAQ (shared memory / NFQ) Пакеты на инспекцию, вердикты
Snort → SFDataCorrelator unified2 файлы на диске Бинарные события IPS
SFDataCorrelator → PostgreSQL JDBC (localhost) Структурированные события
Rails → PostgreSQL ActiveRecord (localhost) Политики, инвентарь, конфиг
Ключевой момент
FTFD общается с Lina через PTY — буквально отправляет текстовые ASA-команды, как если бы человек печатал в CLI. Это означает что операция "применить политику" — это не атомарная транзакция с rollback, а последовательность команд. Если питание пропадёт на середине — конфиг окажется в промежуточном состоянии.

Lina — ASA,

Lina (/usr/local/sf/bin/lina) — это буквально кодовая база ASA, скомпилированная как обычный Linux userspace процесс. 2.1 Conn table — сердце stateful firewall

Conn table — таблица состояний, которая делает Lina stateful firewall. Каждое разрешённое соединение создаёт запись. Последующие пакеты той же сессии проходят по fast path — без полного прохода через ACL.

Half-open лимиты и защита от SYN flood

Lina отслеживает half-open (незавершённые TCP handshake) соединения отдельно. Через MPF можно настроить лимит на количество одновременных half-open сессий с одного IP — это встроенная защита от SYN flood без отдельного IPS правила.

ciscoasa# show conn count
2847 in use, 12453 most used

ciscoasa# show local-host 192.168.1.10
Interface inside: 192.168.1.10
  Curr Conn: 142/unlimited  embryonic: 3/unlimited

# embryonic = half-open сессии

ciscoasa# clear conn address 192.168.1.10
# сброс всех соединений с конкретного IP — безопасно на prod
# НО: приведёт к tcp-not-syn на следующих пакетах этих сессийdiagnostic-cli
После failover или перезагрузки
Conn table не переживает перезагрузку (только stateful failover HA синхронизирует её). Первый пакет существующей TCP сессии после reload не будет SYN — он попадёт в show asp drop как tcp-not-syn. Это нормально, клиент сделает reconnect.

2.2 ACL engine и Turbo ACL

В наивной реализации проверка пакета против ACL — это линейный поиск O(n) по списку правил. При 10 000 правил это катастрофически медленно. Lina использует Turbo ACL — binary decision diagram в памяти, который даёт O(1) / O(log n) lookup.

Как компилируется Turbo ACL

При применении ACL командой access-group Lina компилирует весь список в BDD-структуру. Компиляция может занять несколько секунд для очень больших ACL (>50k строк) и потреблять дополнительную RAM. Это видно как spike CPU при деплое политики.

2.3 NAT engine: Object NAT и Twice NAT

NAT в Lina — полная реализация ASA NAT модели, переписанной в версии 8.3. Она принципиально отличается от старого PIX-стиля и разделяется на два типа с чётким порядком применения.

Порядок применения NAT правил

§1
Twice NAT (Manual NAT) — Section 1
Применяется первым. Позволяет задать как source NAT так и destination NAT одновременно. Используется для VPN NAT-exemption и сложных сценариев.
§2
Object NAT (Auto NAT) — Section 2
Применяется вторым. NAT определяется на объекте сети. Простой и декларативный — задаёшь "этот хост всегда NAT'ится вот так".

2.4 Accelerated Security Path (ASP)

2.5 MPF и Application Layer Gateways

MPF (Modular Policy Framework) — механизм применения дополнительных политик к трафику, классифицированному по class-map. В контексте FTD MPF используется прежде всего для Application Layer Gateways (ALG) — инспекции протоколов с динамическими портами.

Зачем ALG нужен рядом со Snort

Snort делает IPS/IDS — матчит сигнатуры против payload. ALG делает принципиально другое: он понимает прикладной протокол, читает управляющую сессию и динамически открывает порты для data-соединений.

Пример с FTP: FTP использует два соединения — управляющее (порт 21) и data (случайный порт, который сервер объявляет в команде PORT). Статический ACL не может знать этот порт заранее. MPF inspect ftp читает PORT команду в управляющем соединении и автоматически открывает нужный порт в conn table — без изменения ACL.

# Типичная MPF конфигурация (генерируется FMC автоматически)
policy-map global_policy
 class inspection_default
  inspect ftp
  inspect sip
  inspect h323 h225
  inspect tftp
  inspect icmp
  inspect dns maximum-length 1500

service-policy global_policy globalASA config / diagnostic-cli

3.1 DAQ — Data Acquisition Layer

DAQ (Data Acquisition Library) — абстракция источника пакетов, придуманная Sourcefire. Snort не работает напрямую с NIC или с Linux network stack. Вместо этого — pluggable DAQ интерфейс, позволяющий получать пакеты из разных источников через одно API.

Доступные DAQ модули

МодульИсточник пакетовПлатформа

nfqNetfilter Queue — пакеты из iptablesНекоторые виртуальные платформы
sfdaq (внутренний)Shared memory от LinaФизические платформы FPR

Как Lina передаёт пакеты в Snort

На физических платформах используется shared memory IPC: Lina записывает пакеты в общий буфер в памяти (huge pages), Snort читает из него через DAQ модуль. Это zero-copy — никакого syscall overhead на каждый пакет.

Inline vs Passive (IDS) режим

РежимПоведениеПрименение
Inline (IPS) Snort в разрыве трафика. Вердикт block реально дропает пакет через Lina. Продакшн IPS — блокировка атак
Passive (IDS) Snort получает копию трафика. Только генерирует alert, не блокирует. Мониторинг без воздействия на трафик
Inline with fail-open При перегрузке или падении Snort — трафик пропускается без инспекции. Когда availability важнее security
Fail-open и безопасность
При высокой нагрузке когда Snort не успевает обрабатывать пакеты — в режиме fail-open трафик проходит без инспекции. Это означает что в пиковой нагрузке (DDoS, массовый сканер) атаки могут не детектироваться. Мониторь CPU и drop counters Snort.

3.2 Декодер: разбор заголовков

Первая стадия обработки — декодер разбирает заголовки всех уровней и строит внутреннее представление пакета (Packet структура). Это единственный контекст который видят препроцессоры и detection engine.

Что декодируется

Ethernet (802.3, 802.1q VLAN, QinQ, 802.11) → IP (v4 и v6, опции, фрагменты) → TCP/UDP/ICMP/ICMPv6 → начальный разбор application layer (порты, флаги). Декодер также обнаруживает аномалии заголовков и генерирует события decode класса.

Декодер пересобирает IP фрагменты до передачи в препроцессоры. Это критично: многие атаки пытаются спрятать payload в фрагментах, рассчитывая что IDS обработает их по отдельности и не увидит целую сигнатуру.

3.3 Препроцессоры: stream5, http_inspect, appid

Препроцессоры — самый важный слой Snort. Их задача: нормализовать трафик, пересобрать потоки, и сделать из "потока пакетов" осмысленный контекст который уже можно матчить по правилам.

stream5 — TCP reassembly

Без stream5 Snort видит отдельные TCP пакеты. Большинство атак живут на уровне потока: HTTP запрос может занимать несколько пакетов, SQL injection размазан по segments. stream5 пересобирает TCP сессии и предоставляет detection engine полный поток.

Target-based mode: разные OS по-разному обрабатывают overlapping TCP segments (когда два сегмента перекрываются по sequence numbers с разным содержимым). Linux берёт новый сегмент, Windows — старый. Классическая атака — отправить overlapping segments зная как именно IDS пересоберёт поток vs как это сделает целевая OS.

stream5 с policy linux пересобирает поток точно так же как Linux хост. Атака с overlapping segments не пройдёт незамеченной.

# Конфиг stream5 (часть snort.conf)
preprocessor stream5_global: \
  track_tcp yes, \
  track_udp yes, \
  track_icmp no, \
  max_tcp 262144, \
  max_udp 131072

preprocessor stream5_tcp: \
  policy linux, \
  detect_anomalies, \
  require_3whs 180, \
  overlap_limit 10, \
  small_segments 3 bytes 150, \
  timeout 180snort.conf

  msg:"Path traversal attempt";
  flow:established,to_server;
  http_uri;  # матчим нормализованный URI
  content:"/../"; nocase;
  sid:1001; rev:3;

3.4 Detection engine и Aho-Corasick

Detection engine — стадия где происходит матчинг правил против нормализованного трафика. Центральный алгоритм — Aho-Corasick, позволяющий искать все паттерны из всех правил за один проход по данным.

Анатомия правила Snort

alert tcp $EXTERNAL_NET any -> $HOME_NET $HTTP_PORTS (

  # ─ Метаданные ─────────────────────────────────────
  msg:"ET WEB_SERVER SQL injection via URI";
  classtype:web-application-attack;
  
  # ─ Контекст потока ────────────────────────────────
  flow:established,to_server;  # только установленные, к серверу
  
  # ─ Буфер и контентные опции ───────────────────────
  http_uri;                    # работаем с нормализованным URI
  content:"/login"; nocase;   # обязательная "якорная" строка
  
  # ─ Дополнительные матчи ───────────────────────────
  content:"' OR "; nocase; distance:0;  # в том же буфере
  
  # ─ PCRE для сложных паттернов ─────────────────────
  pcre:"/(\\'|%27).*(OR|%4F%52).*(\\d+=\\d+)/iU";
  
  # ─ Идентификаторы ─────────────────────────────────
  sid:2019401; rev:5;
)Snort rules

Aho-Corasick: почему это быстро

Наивный подход: для каждого пакета перебрать все 10 000 правил и проверить каждый content. Это O(n×m) где n — размер пакета, m — число паттернов. С тысячами правил — неприемлемо.

Aho-Corasick строит из всех строковых паттернов единый конечный автомат. За один проход по пакету O(n) находятся все совпадения со всеми паттернами одновременно. Добавление новых правил означает перекомпиляцию автомата — это происходит при деплое новых правил и занимает несколько секунд.

Приоритет вердиктов

Если несколько правил матчат один пакет: drop/block приоритетнее alert приоритетнее pass. Правило pass можно использовать для явного исключения из детекции (whitelist).

4.3 Жизненный цикл деплоя политики

Нажатие Deploy в FMC запускает многоэтапный процесс, который важно понимать чтобы диагностировать failed deployments.

01
Validation

02
Generation
FMC генерирует из объектов политик: набор ASA CLI команд для Lina, файлы .rules для Snort, конфиг препроцессоров в snort.conf / snort.lua, Platform Settings. Это может занять 10–120 секунд для сложных политик.
03
Transfer
Сгенерированный пакет передаётся на managed device через SFTUNNEL. При плохом канале — это узкое место. Файлы правил Snort могут быть десятки мегабайт.
04
Lina apply
FTFD отправляет ASA команды в Lina через Unix socket. Lina применяет их последовательно. Это не атомарная операция — если что-то пойдёт не так на середине, Lina будет в промежуточном состоянии.
05
Snort apply
FTFD записывает новые .rules файлы и сигналит Snort перезагрузить правила. В Snort 2 — SIGHUP, правила перезагружаются ~5-30 секунд. В Snort 3 — live reload без инспекционного разрыва.
06
Verification
FTFD получает от обоих компонентов подтверждение успешного применения и сообщает FMC результат. FMC сохраняет "last successful deploy" timestamp.

6.1 Карта L1–L7: кто за что отвечает

Ключевая путаница у админов, привыкших к классическому L3/L4 firewall-мышлению: в FTD слои модели OSI обрабатываются разными процессами, а не одним стеком. Ниже — построчная раскладка.

Слой OSIКто обрабатываетЧто происходит
L1 Физический NIC firmware + DPDK PMD / kernel driver Автосогласование, SFP-диагностика (show interface → Rx/Tx power), на DPDK-платформах линк-статус опрашивается поллингом, а не прерыванием
L2 Канальный Lina (bridge/BVI код) + Linux net_device MAC-таблица, 802.1Q теги снимаются на входе в sub-interface, ARP — отдельная таблица внутри Lina, не ip neigh в Linux
L3 Сетевой Lina routing engine Своя RIB/FIB, независимая от ip route хоста; сюда же — un-NAT на входе, NAT на выходе
L4 Транспортный Lina conn table + ASP TCP state machine (SYN/SYN-ACK/ESTAB), TCP normalization (randomize seq, MSS clamp), UDP псевдо-состояние по таймауту
L5–6 Сессионный / представления Lina MPF/ALG + Snort SSL-модуль ALG перезаписывает адреса внутри payload (FTP PORT/PASV, SIP), TLS 1.2 decrypt-and-inspect снимает представление (шифрование) прежде чем данные уйдут в L7

Где физически теряется видимость слоя

802.1Q-тег виден Lina на sub-interface, но не виден Snort — DAQ передаёт Snort уже декапсулированный L3/L4 payload конкретного VLAN-контекста, а не сырой Ethernet-фрейм с тегом. Поэтому правила Snort никогда не матчатся на VLAN ID напрямую — только через привязку к zone/interface.

6.2 NUMA, RSS/RPS и CPU affinity

На многоядерных платформах (FPR2100+) производительность определяется не только тем, «сколько ядер», а тем, как трафик распределён между ними на самом низком уровне — до того как пакет вообще увидит Lina.

RSS на NIC — первое разделение

Receive Side Scaling — функция самой сетевой карты: она хэширует 5-tuple (src/dst IP, src/dst port, proto) и раскладывает пакеты по нескольким RX-очередям аппаратно, ещё до DPDK. Каждая очередь закреплена за конкретным CPU core / DPDK lcore.

RPS — программный аналог для FTDv

На виртуальных платформах без DPDK используется Receive Packet Steering — программное распределение через kernel, настраиваемое через /sys/class/net/*/queues/rx-*/rps_cpus. Это компенсирует отсутствие RSS в паравиртуализированных NIC (virtio, VMXNET3 без поддержки множественных очередей).

6.5 Failover изнутри: LAN link и state sync

Active/Standby и Active/Active failover выглядят как единая "магическая" фича, но состоят из двух независимых механизмов на разных уровнях.

01
Failover link — control plane
Отдельный (обычно физический) интерфейс между узлами. Передаёт hello-пакеты каждые 1с (по умолчанию) и конфигурационные команды — те же ASA CLI команды, что FTFD отправляет в Lina, реплицируются на peer через этот канал.
02
Stateful link — data plane
Может быть тем же интерфейсом или отдельным. Передаёт состояние conn table, xlate table, состояние VPN SA в реальном времени — именно это обеспечивает "невидимый" failover для установленных TCP-сессий.
03
Snort и FMC — не синхронизируются автоматически так же
Snort на standby узле запускается независимо со своим локальным конфигом, полученным при последнем деплое от FMC — а не реплицируется через failover link. Рассинхронизация версий политики между active/standby возможна, если один узел пропустил деплой.

INSPECT-цепочка
и fw monitor

Пакет внутри kernel-модуля fw проходит не через один монолитный "firewall check", а через последовательность именованных модулей — chain. Понимание этой цепочки и умение смотреть пакет в конкретной точке через fw monitor — это то, что заменяет Check Point-администратору Cisco'вский packet-tracer.

2.1 fw ctl chain: модули inbound/outbound

Chain — упорядоченный список обработчиков, часть из которых стандартные (firewall, NAT), часть добавляются продуктами (VPN, IPS, Application Control) как отдельные "звенья".

[Expert@gw-01:0]# fw ctl chain
in chain (16 entries):
  0: -7f800000 (00000001) <fw_dip_in>
  1: -7dff5259 (00000001) <pkt_alloc_fwd_chain>
  4: -6ffffff8 (00000001) <vpn_decrypt>
  5: -5ffffff8 (00000001) <fw_conn_in>    // conn table lookup
  6: -4ffffff8 (00000001) <asm_in>        // virtual reassembly
  7: -3ffffff8 (00000001) <fw_inbound>    // rulebase match, INSPECT
  9: -1ffffff8 (00000001) <cmi_in>         // Context Mgmt Infra — IPS/APCL hook

out chain (14 entries):
  0: -7f800000 (00000001) <fw_dip_out>
  5: -5ffffff8 (00000001) <fw_outbound>
  6: -4ffffff8 (00000001) <vpn_encrypt>
  9: -1ffffff8 (00000001) <fw_natr_out>   // NAT rewrite на выходеExpert mode

Порядок в этом списке — не декоративный: он буквально определяет последовательность обработки. fw_conn_in (поиск в conn table) стоит раньше fw_inbound (полный rulebase match) — именно поэтому уже установленные соединения не гоняются заново по всей rulebase на каждый пакет.

2.2 fw monitor: позиции i/I/o/O

fw monitor — встроенный packet capture, который в отличие от tcpdump показывает пакет сразу в нескольких точках прохождения через chain, что позволяет увидеть эффект NAT, VPN-декапсуляции и решения firewall в одном выводе.

ПозицияЧто означает
ipre-inbound — пакет только вошёл в интерфейс, до virtual reassembly и rulebase
Ipost-inbound — после прохождения inbound chain (после NAT/rulebase decision на входе)
opre-outbound — перед выходной цепочкой
Opost-outbound — последний момент перед выходом на интерфейс, после NAT-rewrite
# Классический пример: увидеть NAT "до" и "после" одним запуском

[I] 10.0.0.10 -> 8.8.8.8                      # после rulebase — разрешён
[o] 10.0.0.10 -> 8.8.8.8                      # перед выходом

Золотое правило диагностики Check Point
Если пакет виден в [i], но не виден в [I] — значит его дропнули на входной цепочке (rulebase, anti-spoofing, VPN-декрипт не удался). Если виден в [I], но не в [o] — проблема в routing decision между chains. Это единственный инструмент, который показывает не просто "разрешено/запрещено", а где именно в цепочке пакет исчез.

SecureXL —
слой ускорения

Полный проход через INSPECT-цепочку для каждого пакета — дорогая операция. SecureXL — механизм, который после первого пакета сессии запоминает решение ("template") и обрабатывает последующие пакеты по сокращённому пути, минуя большую часть цепочки.

3.1 Три пути пакета

Accelerated path vs Medium path vs Slow path (F2F)
Accelerated path (SXL)полностью в sim-модуле, чистый L3/L4, минуя fw ctl chain целиком
Medium path (PXL / MPXL)частичный проход — нужна L7-инспекция (IPS/APCL), но conn table уже matched
Slow path / F2F (Firewall-to-Firewall)полный проход через fw kernel module, все chain-модули

F2F (обычный полный путь через fw модуль) — не "плохой" путь, а обязательный для первого пакета любой новой сессии (нужно matched правило и создана запись в conn table) и для трафика, который в принципе нельзя ускорить: фрагментированные пакеты, некоторые виды NAT, VPN handshake, любой трафик, требующий L7-decision.

3.2 Templates и почему трафик уходит в F2F

После того как первый пакет сессии прошёл полный путь и был разрешён, SecureXL может создать template — компактное правило "трафик с такими характеристиками — сразу разрешать" — которое живёт в sim-модуле и обрабатывает последующие пакеты без обращения к полной rulebase.

Глава 04

CoreXL —
многоядерность

SecureXL ускоряет обработку одного пакета. CoreXL решает другую задачу — параллелизм: как распределить нагрузку между физическими ядрами CPU, при том что классический kernel-firewall исторически был однопоточным (одна блокировка на всю conn table).

4.1 SND vs FW worker instances

CoreXL делит ядра на две роли:

  • SND (Secure Network Distributor) — принимает пакеты с NIC, выполняет ту же роль что RSS/RPS в главе про Cisco: хэширует по 5-tuple и раскладывает по FW worker instances. Также именно SND выполняет большую часть accelerated-path SecureXL логики
  • FW worker instance — полноценная копия fw kernel module со своей независимой INSPECT-таблицей состояний, обрабатывающая "свою" долю трафика
[Expert@gw-01:0]# fw ctl affinity -l -a
CPU 0:  fw_0 (fwk) eth0 eth1  # SND часто совмещён с ядром 0
CPU 1:  fw_1 (fwk instance 1)
CPU 2:  fw_2 (fwk instance 2)
CPU 3:  fw_3 (fwk instance 3)

[Expert@gw-01:0]# fw ctl multik stat
ID | Active | CPU |  Connections
 0 | yes    |  1  |  15230
 1 | yes    |  2  |  15104
 2 | yes    |  3  |  14980Expert mode
Важный нюанс: одна сессия — одно ядро
В отличие от stateless-балансировки, у CoreXL все пакеты одной сессии всегда обрабатываются на одном и том же worker instance (иначе пришлось бы синхронизировать conn table между ядрами на каждый пакет — дорого). Это значит что throughput одного-единственного "тяжёлого" потока (например iperf в один поток) физически ограничен производительностью одного ядра, сколько бы ядер ни было в системе.

4.2 fw ctl affinity и CPU pinning

Количество SND-ядер и FW worker instances настраивается вручную (или через Dynamic Balancing в новых версиях) в зависимости от профиля нагрузки — много мелких коротких сессий требует больше SND, тяжёлая L7-инспекция требует больше worker instances.

# Привязать конкретный интерфейс к конкретному SND-ядру вручную
[Expert@gw-01:0]# fw ctl affinity -s -i eth2 0Expert mode
Dynamic Dispatcher (R80.20+)
В новых версиях появился Dynamic Balancing — SND сам перераспределяет нагрузку между worker instances на лету при выявлении "горячих" ядер, вместо статичного хэша по 5-tuple на весь срок жизни соединения. Это снижает необходимость ручной affinity-настройки, но не отменяет фундаментальное ограничение "одна сессия — одно ядро" в моменте.

Глава 05

Threat Prevention
и CMI

L3/L4 INSPECT и SecureXL — быстрый, но "плоский" путь. Как только политике нужно заглянуть внутрь HTTP, DNS, SMB или сопоставить сигнатуру — в игру вступает Context Management Infrastructure, стоящая между чистым kernel firewall и продуктами глубокой инспекции.

5.1 Context Management Infrastructure

CMI — общая инфраструктура (модуль cmi_loader, упомянутый в главе 1), на которую "навешиваются" разные Blade'ы: IPS, Application Control, Content Awareness, Anti-Bot, Anti-Virus. Она берёт на себя разбор потока (Passive Streaming Library — TCP reassembly для L7), чтобы каждый Blade не реализовывал это заново.

Место CMI в fw chain

↓

Отличие от medium/slow path из главы 3
Именно необходимость пройти через CMI — главная причина попадания трафика в PXL (medium path) вместо чистого accelerated: SecureXL физически не может "срезать путь" мимо L7-парсера, если политика требует его сработки для этой сессии.

5.2 IPS engine и Application Control

IPS-сигнатуры (протекции) исполняются в kernel space через CMI — в отличие от Snort у Cisco, который целиком userspace-процесс. Application Control в первую очередь классифицирует по known-signature паттернам локально, но для новых/неизвестных приложений может обращаться к ThreatCloud (облачная база Check Point) — единственная точка, где инспекция уходит за пределы шлюза.

Глава 01

FortiOS —
Linux под замком

В отличие от Cisco (expert → bash) и Check Point (Expert mode → root bash), FortiOS сознательно не даёт админу прямого доступа к общей Linux-оболочке. Ядро под капотом — модифицированный Linux, но всё взаимодействие идёт только через проприетарный CLI: config / execute / diagnose. Это фундаментально другая философия эксплуатации.

Архитектурный обзор: закрытая модель

FortiOS исторически строился как единый образ прошивки (не "набор userspace-процессов поверх стандартного дистрибутива", как позиционируют Lina/Snort или fwd/CPM). Ядро — модифицированный Linux, поверх него — набор проприетарных демонов, но нет ни bash, ни пакетного менеджера, ни файловой системы, доступной для произвольного редактирования. Это осознанный компромисс Fortinet: меньше поверхность атаки и меньше шансов рассинхронизировать конфиг руками — но и меньше диагностической свободы, чем у Cisco/Check Point.

Главная архитектурная особенность аппаратных FortiGate — Network Processors (NP6, NP7 в новых моделях): отдельные ASIC-чипы, которые могут обрабатывать пакеты установленных сессий вообще не привлекая CPU и kernel устройства. 2.1 Что такое NPU offload

Глава 03

Flow-based
vs Proxy-based

Это развилка, определяющая всё: насколько глубока инспекция, насколько она быстра, и совместима ли сессия с NPU-офлоадом из главы 2. Каждый security-профиль (AV, IPS, Web Filter, App Control) на FortiGate можно применять в одном из двух режимов — и это выбор, а не данность.

3.1 Single-pass flow-based

Flow-based инспекция построена по принципу single-pass: пакеты анализируются "на лету", по мере прохождения, без полной буферизации содержимого сессии. Сигнатурный движок (DFA — deterministic finite automaton) ищет паттерны в потоке байт инкрементально, не дожидаясь пока накопится весь объект (файл, HTTP-ответ и т.д.) целиком.

→

→

инкрементальный pattern match
→
Egress

Плюс — низкая задержка и совместимость с последующим NPU-офлоадом сессии (после того как первые пакеты прошли инспекцию и сессия признана безопасной). Минус — некоторые виды детекции (например точная блокировка файла целиком по хэшу, а не только по сигнатуре в потоке) в чистом flow-режиме менее надёжны, чем при полной буферизации объекта.

3.2 Proxy-based: wad и полная реассемблинг

В proxy-режиме FortiGate буквально выступает прокси для сессии: TCP-соединение терминируется на устройстве, содержимое полностью реассемблируется и передаётся демону wad, который может пересобрать весь объект (файл, HTTP-транзакцию) прежде чем принять решение, и только затем открывает/устанавливает соединение с реальным получателем.

Именно proxy-режим используется для SSL/TLS Deep Inspection: wad расшифровывает трафик, инспектирует содержимое, и пересобирает TLS-сессию к клиенту уже с сертификатом, подписанным локальным CA устройства (отсюда требование установить корневой сертификат FortiGate на клиентские машины).

Цена полноты
Proxy-режим структурно несовместим с NPU-офлоадом (глава 2.3) — трафик обязан идти через CPU и userspace-процесс wad на всю длительность сессии. Это осознанный trade-off: глубина инспекции против чистой пропускной способности.

Глава 04

CP9
content processor

Если NP6/NP7 — это про то, чтобы вообще не трогать CPU для уже установленных сессий, то CP9 (Content Processor) — второй ASIC-чип, который ускоряет саму работу CPU там, где сессию всё же приходится обрабатывать: криптографию и сигнатурный поиск.

4.1 Роль: крипто и pattern matching

ФункцияЧто офлоадится в CP9
IPsec / SSL VPNСимметричное шифрование/дешифрование (AES, SHA) — CP9 выполняет крипто-операции аппаратно вместо CPU
SSL Deep InspectionРасшифровка/зашифровка TLS-сессий в proxy-режиме частично разгружается на CP9, снижая нагрузку на CPU даже при полном proxy-пути из главы 3
IPS / AV сигнатурный поискPattern matching (тот же класс задач, что DFA у ipsengine) ускоряется аппаратно для профилей, где чип поддерживает конкретный тип сигнатур
Отличие от NP6/NP7 — важно не путать
NP-чип решает "не гонять пакет через CPU вообще". CP9 решает "если пакет всё равно на CPU — сделать тяжёлые вычисления (крипто, паттерн-матчинг) быстрее". Это разные уровни офлоада: NPU — про обход обработки, CP9 — про ускорение самой обработки. На платформах без NP-чипов (некоторые младшие модели) CP9 может быть единственным источником аппаратного ускорения.

Fallback на CPU — не всегда очевиден
Некоторые криптографические комбинации (редкие/устаревшие алгоритмы, определённые режимы аутентификации) не поддерживаются CP9 и незаметно откатываются на программную обработку CPU. Если IPsec-туннель "почему-то" грузит CPU сильнее ожидаемого — первым делом стоит свериться с списком алгоритмов, аппаратно поддерживаемых конкретной ревизией CP9 на данной модели.

Глава 06

FortiManager,
конфиг и FortiGuard

Управляющая плоскость FortiGate состоит из трёх независимых частей: канал до FortiManager (FGFM) для централизованного управления, локальная config database самого устройства с версионированием, и отдельный внешний сервис FortiGuard для сигнатур/категоризации, работающий даже без FortiManager вообще.

6.1 FGFM: протокол FortiManager

FortiManager управляет одним или множеством FortiGate через собственный протокол FGFM (FortiGate-FortiManager protocol, TLS поверх TCP/541). В отличие от Cisco FMC (полноценный REST API + генерация конфигурации) или Check Point CPM (объектная PostgreSQL база), FortiManager хранит конфигурацию как ADOM (Administrative Domain) с Policy Packages — пакетами политик, которые устанавливаются на конкретные устройства целиком.

FortiGuard — облачная инфраструктура Fortinet, обеспечивающая два принципиально разных вида сервиса: доставку обновлений сигнатур (IPS/AV/Application Control базы, скачиваются периодически и хранятся локально) и living-запросы категоризации в реальном времени (веб-категории URL, репутация IP для антиспам/веб-фильтра) — для последнего устройству нужна постоянная связность с облаком, локального кэша обычно недостаточно для полного покрытия базы.

1.2 NGFW Novum: DPDK + VPP

Ideco NGFW Novum — принципиально другая платформа: по данным технического описания вендора, решение построено на собственном сетевом стеке с использованием DPDK (прямой доступ к сетевым картам, минуя стандартный путь ядра — та же техника kernel bypass, что использует Cisco Lina, см. главу про FTD) и VPP — Vector Packet Processing, open-source фреймворк проекта FD.io, изначально развивавшийся Cisco и позже переданный в Linux Foundation. Заявленная производительность — до 200 Гбит/с и до 1 миллиона TCP-сессий в секунду без аппаратных ускорителей (то есть на общего назначения x86, не на NP-подобных чипах как у Fortigate).

Архитектурная разница классического UTM и Novum
Ideco UTM (классика)стандартный Linux kernel networking + собственные модули поверх
Ideco NGFW NovumDPDK (kernel bypass) + VPP (vector packet processing) + микросервисы

Собственный компилятор правил (по формулировке вендора) — заявлена обработка 100 000 правил для 500 000 пользователей и групп безопасности без деградации, что структурно похоже на задачу, которую в главе про Check Point решает компиляция в INSPECT-код, а в главе про PT NGFW (глава 3) решается параллельным сопоставлением правил вместо последовательного перебора.

VPP — не изобретение Ideco, а известный строительный блок
Важно понимать: VPP — это open-source технология, которую использует не только Ideco (в мире на VPP также строятся некоторые решения операторского класса и часть облачных vSwitch). Ценность конкретно продукта Ideco здесь не в изобретении VPP, а в инженерной работе по интеграции VPP с собственным движком L7-инспекции, IPS-сигнатурами и микросервисной моделью управления — это не хуже и не лучше "изобретения велосипеда с нуля", просто другой инженерный выбор.

UserGate строит свою линейку вокруг собственной операционной системы UGOS (иногда пишется UG OS) начиная с 2013 года — дольше, чем у Ideco Novum или PT NGFW есть история эксплуатации. Ключевое маркетинговое заявление вендора — полностью собственная разработка "без стороннего кода и модулей".

2.1 UGOS: заявление о "с нуля"

В официальных материалах UserGate прямо говорится, что в основе UGOS не используется чужой исходный код и сторонние модули — заявление, которое стоит воспринимать с профессиональной осторожностью: полностью независимая от Linux/BSD экосистема драйверов, файловых систем и сетевого стека — крайне трудоёмкая инженерная задача, которую в мире решали единицы компаний (например, часть проприетарных ASIC-платформ операторского класса). Вендор не публикует технических деталей, подтверждающих или детализирующих это заявление на уровне исходного кода или сборки ядра.

Как к этому относиться профессионально
Для практической эксплуатации это заявление не так важно, как для маркетинга: что действительно имеет значение для админа — набор доступных диагностических команд, поведение при отказах и задокументированное API, а не то, использует ли ядро под капотом код с открытой лицензией. Стоит фиксировать это как позицию вендора, а не как проверяемый технический факт, и строить диагностику от задокументированного поведения CLI (см. 2.2), а не от предположений о внутреннем устройстве ядра.

2.3 DCFW и FPGA-ускорение

Data Center Firewall (DCFW) — старшая линейка UserGate для ЦОД и телеком-инфраструктуры, анонсированная как построенная на собственных аппаратных платформах с применением FPGA-ускорения (Field-Programmable Gate Array — перепрограммируемая логика, в отличие от фиксированных ASIC вроде NP6/NP7 у Fortigate).

FPGA vs ASIC — принципиальная разница подхода
ASIC (Fortigate NP6/NP7) — заточен под конкретную задачу намертво на этапе производства чипа: очень быстро, но негибко. FPGA — перепрограммируемая логика: чуть медленнее "идеального" ASIC на теоретическом пределе, но позволяет обновлять логику офлоада без замены железа — вероятно осознанный выбор UserGate на быстро меняющемся и не самом зрелом пока рынке отечественных NGFW, где алгоритмы обработки могут дорабатываться быстрее, чем окупается цикл разработки специализированного ASIC.

По данным профильных изданий, ранняя платформа (получившая внутреннее развитие в направлении UserGate FG) продемонстрировала кратный (более чем в 4 раза) прирост пропускной способности относительно чисто CPU-based обработки, заявленный потолок — около 160 Гбит/с — что для российского рынка на момент анонса позиционировалось как рекордный показатель.

2.4 Экосистема SUMMA

Как и у остальных вендоров этой главы, NGFW — не изолированный продукт, а часть более широкой платформы. UserGate SUMMA объединяет NGFW/DCFW, Management Center (централизованное управление), Log Analyzer, SIEM, WAF, endpoint-агент UserGate Client (EDR/NAC-функциональность) и решения для АСУ ТП (ICS Client) — идеологически близко к экосистемам MaxPatrol/PT (глава 3) и FortiManager/FortiAnalyzer у Fortigate, только под общим брендом "ячеистой архитектуры кибербезопасности" (mesh cybersecurity architecture) вендора.

Единый термин, разное содержание у каждого вендора
Термины "экосистема" и "централизованное управление" у Ideco Center, UserGate SUMMA/Management Center и Positive Technologies (глава 3) означают структурно разные вещи по глубине интеграции и API — при выборе стоит запрашивать у вендора конкретный уровень API-покрытия и SLA техподдержки для конкретной задачи, а не полагаться на маркетинговое сходство формулировок.
Глава 03

Positive Technologies
PT NGFW

PT NGFW (ноябрь 2024, разработка "с нуля" за два года) — из трёх вендоров этой главы даёт наиболее конкретно раскрытую архитектуру: управляющий директор и директор по продуктам Positive Technologies Денис Кораблёв публично описал внутреннюю механику обработки пакетов на техническом уровне, что редкость для этого рынка.

3.1 Отказ от Linux network stack

Ключевое архитектурное решение — полный отказ от стандартной сетевой обработки пакетов, встроенной в Linux, с переносом обработки в пользовательское пространство. По формулировке вендора это "ноу-хау" — модернизированный стек TCP/IP, разработанный Positive Technologies самостоятельно, а не адаптация существующего kernel-bypass фреймворка вроде DPDK или VPP (которые используют Ideco Novum и, судя по всему, платформы других вендоров).

Разница с подходом Ideco Novum из главы 1
Ideco Novum строит свой data path поверх существующих open-source строительных блоков (DPDK для доступа к NIC, VPP для векторной обработки пакетов) — типичный и проверенный индустрией путь. PT NGFW, по заявлению вендора, написал сопоставимый по функции слой полностью самостоятельно. Это не делает один подход автоматически лучше другого — но это разные компромиссы между скоростью выхода на рынок (готовые библиотеки) и полным контролем над оптимизацией под конкретную задачу (собственная разработка).

3.2 Zero-copy: проекция буфера NIC в RAM

Конкретный механизм, описанный вендором: данные, попадающие в буфер сетевой карты, не копируются и не обрабатываются напрямую в этом буфере. Вместо этого создаётся их разметка и проекция в оперативную память через DMA (Direct Memory Access) — прямой доступ к памяти в обход CPU для самого копирования. Вся дальнейшая обработка (сопоставление с правилами фильтрации) идёт через указатели в этой RAM-проекции, не трогая исходный буфер NIC.

Практическое следствие, на которое отдельно указал Кораблёв: скорость разбора пакетов в такой модели перестаёт зависеть от пропускной способности самой сетевой карты. Пример из презентации вендора — интерфейс на PCIe 3.0 (8 GT/s на линию) сам по себе не становится потолком, потому что центральный процессор с его тактовой частотой и многопоточностью успевает разобрать трафик быстрее, чем ограничивает физический канал карты. Это отличается от ситуаций, где узкое место — именно манипуляции с данными в буфере NIC.

Где это особенно заметно: мелкие пакеты
По словам представителя Positive Technologies, наибольшую нагрузку на любой NGFW создают не большие потоки данных, а большое количество мелких пакетов на высокой скорости. Вендор заявляет, что на таком трафике PT NGFW работает в 2–3 раза быстрее конкурентов при сохранении полного L7-анализа — это прямое следствие того, что zero-copy подход не тратит циклы CPU на копирование данных из буфера на каждый мелкий пакет.

3.3 Параллельное сопоставление правил

Второе заявленное "ноу-хау" — собственный (на момент публикации технического разбора — незапатентованный) алгоритм сопоставления трафика с правилами фильтрации, который проверяет весь массив правил параллельно, а не последовательным перебором (что является узким местом для многих firewall-движков при разрастании rulebase до сотен тысяч записей).

Независимый тест показал кратно меньшие, но подтверждённые цифры на конкретном стенде. Для любого NGFW (не только российского) стоит различать datasheet-максимумы и цифры независимых тестов на вашем реальном профиле трафика — это общее правило, не специфичное для PT NGFW.

3.4 Виртуальные контексты и HA

"Виртуальные контексты" PT NGFW — логическое разделение одного физического устройства на несколько независимо управляемых логических firewall, концептуально близкое к VDOM у Fortigate (глава 2 предыдущего документа) и multiple instance security context у некоторых других вендоров. Для каждого устройства автоматически создаётся контекст Default; дополнительные контексты формируются через субинтерфейсы, привязанные к нему, но управляемые раздельно.

Отказоустойчивость поддерживает два режима:

  • Active-Active — внешний балансировщик распределяет нагрузку между узлами кластера
  • Active-Passive/Standby — реплицируется полный snapshot состояния активного узла на резервный; при отказе или деградации канала происходит переброс и синхронизация сессий без потери данных
Заявленное преимущество: меньше избыточного резервирования
По утверждению вендора, благодаря архитектуре PT NGFW не требуется держать существенный избыточный запас пропускной способности "на всякий случай" под всплески трафика, характерный для конфигураций без надёжного active-passive механизма — это позволяет линейно масштабировать стек устройств без потерь при добавлении узлов. Как и любое вендорское заявление о масштабировании — стоит проверять на собственном профиле нагрузки перед архитектурными решениями с долгосрочными последствиями.

3.5 PT ESC и экосистема

Сигнатурная база (заявлено более 10 000 сигнатур на момент запуска) поддерживается PT Expert Security Center (PT ESC) — профильным экспертным подразделением, которое, по словам представителей компании, насчитывает порядка 200 человек. PT NGFW интегрируется с остальной экосистемой Positive Technologies: MaxPatrol SIEM (корреляция событий), PT Sandbox (детонация подозрительных файлов), PT Network Attack Discovery — NAD (сетевой анализ атак постфактум по трафику).

Отдельно у продукта есть выделенная ветка правил для защиты специфичного для российского рынка ПО — в частности, для платформы «1С-Битрикс», доля уязвимых сайтов на которой, по данным экспертов PT, заметно росла в 2024–2025 годах. Это пример локализации экспертизы под конкретный рынок, а не универсальная практика западных NGFW.

Модельный ряд на момент запуска
Линейка состоит из семи моделей: 1010, 1050, 2010, 2020, 2050, 3010, 3040 — от компактного филиального устройства до старшей платформы для ЦОД. Все аппаратные платформы — российского производства, на процессорной архитектуре x86 общего назначения (без собственных ASIC-чипов, в отличие от Fortigate NP6/NP7).

Отдельного упоминания заслуживает патент «Кода Безопасности» на технологию обработки сетевых пакетов для высокопроизводительного межсетевого экрана — по заявлению разработчика, именно эта разработка обеспечивает существенный прирост пропускной способности МЭ-режима (заявлено до 80 Гбит/с) относительно полного UTM-режима с глубоким анализом (около 11 Гбит/с) — разница на порядок, характерная и для остальных вендоров этого пособия (тот же паттерн видели у Check Point: accelerated path vs F2F, и у Fortigate: NPU offload vs proxy-based).

4.2 Платформа: FreeBSD-наследие

Континент 3.9 — последняя перед 4-й версией — по данным технического обзора, работала на 64-битной программной платформе x86_64 FreeBSD (переход с 32-бит был отдельно отмечен вендором как apгрейд производительности). Для версии 4 вендор публично не раскрывал прямую смену базовой ОС, но косвенный сигнал есть: в инструкциях по развёртыванию тестового стенда Континент 4 на VMware Workstation администраторам предписывается указывать тип гостевой ОС CentOS (and later) x64 при создании виртуальной машины под установочный ISO.

Это инференция, а не подтверждённый факт
Выбор типа гостевой ОС в гипервизоре — практическая настройка (влияет на предполагаемый набор виртуальных устройств и оптимизации), а не официальное заявление об архитектуре. Но выбор именно CentOS (Linux RHEL-семейства), а не «FreeBSD x64» (такой пункт в VMware тоже существует) — заметный сигнал в пользу того, что Континент 4 мог полностью перейти на Linux-ядро вместо продолжения линии FreeBSD из версии 3.x. Официального технического описания уровня "мы перешли с FreeBSD на Linux" в открытых источниках на момент подготовки пособия найти не удалось — это стоит уточнять напрямую у вендора при архитектурном due diligence.

Что подтверждено безотносительно базового ядра: устройство поставляется только в аппаратном исполнении (готовые платформы IPC-10 … IPC-3000NF2), не оснащено DHCP-клиентом на WAN-интерфейсе (сознательное ограничение для appliance с фиксированной сертифицированной конфигурацией), и требует прохождения инициализации через текстовое меню при первом включении — что похоже по духу на первичную инициализацию Check Point Gaia через Clish, только более ограниченно по набору доступных на этом этапе действий.

4.3 Модули и режимы поставки

УБ может разворачиваться в одном из трёх принципиальных режимов — важное архитектурное решение, отличающее Континент от большинства других вендоров этого пособия, где "включить/выключить" security-функции — это вопрос лицензии, а не выбора роли устройства при первичной инициализации.

4.4 ЦУС и Менеджер конфигурации

Управляющая плоскость Континента 4 разделена на два компонента: ЦУС (Центр Управления Сетью) — серверная часть, может быть как отдельным устройством, так и совмещённой с УБ роль; и Менеджер конфигурации — отдельное Windows-приложение для АРМ администратора, устанавливаемое на рабочую станцию, а не веб-консоль. Концептуально это ближе всего к связке Check Point SmartConsole + CPM из главы про Check Point, только без веб-альтернативы — только desktop-клиент.

Инициализация ДСЧ (датчика случайных чисел) при первом запуске Менеджера конфигурации — обязательный шаг, напрямую связанный с требованиями сертификации ФСБ по СКЗИ (криптографическая защита информации): для генерации ключей ГОСТ-шифрования нужен качественный источник энтропии, и вендор явно выносит эту настройку в первый экран, а не прячет как деталь имплементации — разумный подход для продукта, который в первую очередь продаётся как средство криптозащиты, а потом уже как NGFW.

Кластеризация — Active/Passive, без деталей синхронизации в открытом доступе
Как и у остальных вендоров, для отказоустойчивости поддерживается кластер в режиме Active/Passive. В отличие от глав про Cisco (failover link + stateful link отдельно), Check Point (SIC-защищённый heartbeat), Fortigate (FGCP с нюансами NPU-офлоада) — по Континенту в открытых источниках не удалось найти публичного технического описания механизма синхронизации состояния сессий между активным и резервным УБ на уровне протокола. Это не значит, что механизма нет — значит, что публичная документация не идёт вглубь настолько же, насколько у более зрелых по возрасту публичной экосистемы западных вендоров.

Общий паттерн для всех троих
Ни один из трёх российских вендоров пока не даёт администратору того уровня diagnostic CLI, что есть у Cisco (packet-tracer), Check Point (fw monitor) или Fortigate (diagnose debug flow) — не потому что архитектурно это невозможно, а потому что рынок и продукты моложе, а публичная техническая документация для этого уровня диагностики ещё формируется. Это стоит закладывать в операционные ожидания при миграции: часть диагностических задач, тривиальных на Cisco/Check Point, потребует либо обращения в техподдержку вендора, либо ожидания следующих релизов документации.
Общий паттерн номер два: kernel bypass как индустриальный стандарт
Все data path-ориентированные линейки этой главы (Ideco Novum, вероятно PT NGFW) независимо друг от друга пришли к одной и той же идее — обходить стандартный сетевой стек ОС ради производительности. Это тот же принцип, что DPDK у Cisco Lina (глава про FTD) и NP-офлоад у Fortigate: на всех архитектурах NGFW индустрия одинаково упирается в один и тот же физический потолок — накладные расходы на копирование и обработку пакета через общий kernel networking stack — и решает его сходными по духу, хоть и разными по реализации способами.

Два сквозных наблюдения по всем восьми линейкам

Наблюдение 1: kernel bypass — не мода, а физика
Lina/DPDK (Cisco), fw kernel module (Check Point), NP6/NP7 (Fortigate), DPDK+VPP (Ideco Novum), заявленный custom-стек (PT NGFW) — пять принципиально разных инженерных решений одной и той же проблемы: копирование пакета через стандартный kernel networking stack ОС — статистически самое дорогое место в пути пакета на высоких скоростях. Все восемь линеек так или иначе платят инженерную цену, чтобы этого избежать. Разница — в том, чьей ценой: DPDK/VPP берут готовый чужой инструмент (быстрее выйти на рынок), NP-чипы Fortigate — берут ценой негибкости "зашитой в кремний" логики, PT NGFW — ценой полной самостоятельной разработки с нуля.
Наблюдение 2: зрелость diagnostic CLI прямо пропорциональна возрасту продукта на открытом рынке
packet-tracer (Cisco), fw monitor (Check Point), diagnose debug flow (Fortigate) — продукты с более чем 15-летней историей публичной эксплуатации и community. У всех трёх российских NGFW и Континента (продукты 2013–2024 годов на массовом корпоративном рынке NGFW) сопоставимого по глубине и открытости publicly-документированного diagnostic-инструментария пока нет — это не приговор архитектуре, а прямое следствие возраста рынка и объёма накопленной community-экспертизы. При миграции с западного вендора на любой из российских стоит закладывать в план не "он хуже", а "документация и практики диагностики ещё формируются — часть задач потребует прямого контакта с техподдержкой вендора".
